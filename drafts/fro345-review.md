## Findings

1. **Existing UI integration needs a precise event target.** Current FRO-316 requires View history to reach the matching cancellation/location-unknown event, full reason/timestamps, and Last confirmed stage only when supported by actual preceding history. FRO-345 currently promises generic paginated newest-first reads. Specify authorized lookup of the referenced event even when it is outside the first page, and supported predecessor information. Do not infer predecessor from current status or milestone timestamps. FRO-316 keeps all presentation ownership.
2. **Cancellation reason is stored but unreadable through current Shipment detail contracts.** `docs/reference/database.md:1293` stores `freight_shipment.cancellation_reason`; `:1310` requires a nonblank CANCELLED reason. Server `ShipmentOutput.java:9–31` and `src/main/resources/graphql/shipments.graphqls:167–190` expose cancelledAt but no cancellation reason. `ShipmentsRestApi.java:86–88` returns the same shared output. FRO-345 needs an explicit canonical-source mapping into history; do not claim the current API already exposes it. Decide whether the detail contract also needs the field or the event contract alone satisfies the UI.
3. **One operation per successful command needs stronger correlation than existing command UUIDs.** `ShipmentsApiService.java:420,619,724,801,885` generates fresh UUIDs per invocation. Partial-selection child creation has a separate splitCommandId at `:1160`. Grouping existing effects only by equal command_id would split one Shipment creation into multiple operations. Define a durable root operation identity and explicit links to related split/PO/colli effects, including affected identities after removal. Preserve separate source records; avoid heuristic joins.
4. **Retry handling is stated as an outcome without a usable contract.** Current Shipment inputs have no caller idempotency key. Lifecycle guards reject repeats, but that does not resolve a lost success response or protect new comment retries. Specify consistent request identity/outcome reconciliation across adapters, same-request replay, conflicting reuse, concurrent requests and atomic rollback. Distinct intentional identical comments must remain possible; identical text/time is not a deduplication key. Existing PO addMessage accepts only id/message and is not evidence of retry safety.
5. **Chronology and unknown-date representation remain ambiguous.** Dispatch/cancel/unknown/arrival accept occurrence timestamps (`shipments.graphqls:55–86`); the service uses server time when omitted (`ShipmentsApiService.java:1391–1392`). Colli journey has occurred_at but no separate recorded timestamp (`database.md:444–463`). Define whether newest-first means recording or occurrence time and how immutable command order relates to backdated values. Define nullable/precision-preserving occurrence facts for historical ARRIVED creation. Do not fabricate an exact timestamp from a date or recording time from an old occurred_at. Unknown actors remain unknown; PO activity created_by_id is nullable (`database.md:774`).
6. **Comment boundaries are unfinished.** Terminal-state availability is unspecified. The limit is explicitly deferred, so UI/backend validation has no settled maximum. Existing `PurchaseOrdersApiService.java:1386–1398` offers a 2,000-character required-text convention, authenticated actor/server time and transactional write; this is a reference, not an approved Shipment limit. Specify Unicode/whitespace validation consistently, full-text preservation, retry behavior and terminal-state availability. Comment writes should not increment an operational-plan version or invalidate readiness/reviews inadvertently.
7. **Operation coverage needs an explicit boundary.** Notes are not listed in Recorded operations although the introduction refers broadly to successful Shipment operations. State whether Notes use their separate owning audit contract or contribute a linked Shipment operation; comments remain their own stream. Attachments/delivery-note lifecycle is already deferred. Arrival plus handover is one command: current arrival transaction writes handover with confirmedBy=actor and confirmedAt=arrivedAt (`ShipmentsApiService.java:870–881`); do not treat that historical occurrence timestamp as independent proof of entry time or emit a second arrival operation.
8. **Delivery and verification requirements need tightening.** Explicitly coordinate prospective capture with FRO-325/FRO-344 commands and FRO-324 historical creation, so commands cannot ship without their promised history or create competing audit stores. FRO-345 is 0.0.7; FRO-316 presentation is 0.0.9. Backend capture can precede UI; activation must preserve compatible consumers. Exact bounded pagination/cursor behavior, authorized event lookup, adapter contract ownership, append-only protections and preservation of snapshot names/references need verifiable requirements. Replace generic Verification with Context for agents, Decisions and acceptance-mapped read-only Post-deployment verification, separating staging mutation tests from production checks. Current labels also lack a Type/Area; propose Backend/Story only through a separately approved metadata change. Preserve Todo/Pending_Review until explicitly changed.
